# v4.58 变更记录

## 核心问题
用户反馈：很多软件第一次开屏有广告，后边再次启动就没有了。

前三个版本（v4.55→v4.56→v4.57）的修复尝试均未彻底解决问题：
- v4.55：基础版本
- v4.56：逐域名QUIC阻断（60+规则）→ 仍有遗漏域名
- v4.57：全局QUIC阻断 → 仍然有第一次冷启动广告

## 根因分析

QUIC阻断解决了"QUIC协议绕过MITM"的问题，但这只是多个旁路之一。

**真正的根因是：广告SDK域名在路由层没有被阻断。**

冷启动广告的加载流程：
1. App启动 → 请求广告SDK域名（如 `is.snssdk.com`、`ms.snssdk.com`）获取开屏广告
2. 这些请求走HTTPS
3. URL Rewrite / Map Local / Script 都需要MITM解密才能处理HTTPS
4. 如果广告SDK域名不在MITM hostname列表中 → MITM不解密 → 广告请求成功
5. 第一次冷启动时尤其严重，因为App缓存为空，必须请求广告

v4.57的URL-REGEX兜底规则虽然包含了 `pangle`、`pangolin` 等关键词，但：
- URL-REGEX对HTTPS仍需MITM才可见
- 很多广告SDK域名（如 `is.snssdk.com`）不包含这些关键词
- hostname列表有6658字符，无法覆盖所有广告SDK域名

## v4.58 修复方案

**在路由层（[Rule]段）添加DOMAIN-SUFFIX REJECT规则，直接阻断广告SDK域名连接。**

DOMAIN-SUFFIX REJECT 在路由阶段生效，不需要MITM解密，直接拒绝TCP连接。
即使DNS预解析在VPN隧道就绪前完成，连接仍会被路由层拒绝。

## 为什么这次能修复

| 层级 | 机制 | 需要MITM? | v4.57 | v4.58 |
|------|------|-----------|-------|-------|
| [Rule] DOMAIN-SUFFIX REJECT | 路由层拒绝TCP连接 | ❌ 不需要 | 部分覆盖 | ✅ 全面覆盖 |
| [Rule] PROTOCOL,QUIC,REJECT | 路由层拒绝QUIC | ❌ 不需要 | ✅ 已有 | ✅ 保留 |
| [Rule] URL-REGEX REJECT | 需MITM解密HTTPS | ✅ 需要 | ✅ 已有 | ✅ 保留 |
| [URL Rewrite] reject | 需MITM解密HTTPS | ✅ 需要 | ✅ 已有 | ✅ 保留 |
| [Script] type=http-response | 需MITM解密HTTPS | ✅ 需要 | ✅ 已有 | ✅ 保留 |

v4.58 的新增规则全部在路由层生效，**不需要MITM解密**，在TCP连接建立前就拒绝广告SDK域名，确保即使冷启动时也能阻断广告请求。

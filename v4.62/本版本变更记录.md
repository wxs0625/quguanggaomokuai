# 全能去广告精简范围恢复版 v4.62 变更记录

- 基线版本：v4.61
- 发布日期：2026-08-28
- 问题现象：安装 v4.61 后，哔哩哔哩开屏广告仍然存在。用户提供了 Shadowrocket 流量日志（proxy-2026-08-28-221439.db）用于取证。

## 根因分析（流量日志实证）

分析日志中与 B 站相关的 151 条记录，结论与此前所有假设都不同：

1. **MITM 解密完全正常**：`app.bilibili.com` 排在重排后 [MITM] 列表第 1 位，开屏接口全部被解密并进入规则匹配。
2. **开屏接口全部已被拦截**：
   - `x/v2/splash/list`、`x/v2/splash/show`、`x/v2/splash/event/list2` 被 `URL-REGEX ... REJECT-DICT` 拦截 8 次；
   - `x/v2/splash/brand/list` 被全局开屏兜底 `MAP-LOCAL ... REJECT` 拦截 2 次。
3. **但拦截方式是错的**：上述规则返回的是 `{}`（reject-dict / Map Local 空对象），**没有 B 站 API 标准的 `code`/`message`/`ttl` 外壳**。
4. **客户端行为**：B 站 iOS 客户端（9.5.0，日志中 `mobi_app=iphone&build=90500100`）收到 `{}` 后判定为**请求失败**，按容错逻辑**回退展示本地缓存的开屏素材**——所以开屏广告照旧，而且日志里能看到同一接口被连续重试 4 轮（22:14:40–22:14:49），与"失败重试"行为完全吻合。
5. **v4.61 加的请求级 `reject-dict` 是回归放大器**：它在请求阶段就杀掉了连接，导致上游 v4.43/v4.44 设计的 [Body Rewrite] jq 净化（把真实响应里的 `show`/`event_list` 清空、保留 `code:0` 成功外壳）永远得不到执行。也就是说：**净化链路里唯一能返回"合法成功空响应"的规则被兜底规则抢先屏蔽了**。

结论：**开屏广告不是"没拦住"，而是"拦得太粗暴"**——返回失败响应触发客户端缓存回退。

## 修复内容

### 1. 撤销 v4.61 的 B 站开屏请求级 reject-dict（[URL Rewrite]）

删除该条规则并以注释说明原因：

```
# v4.62 哔哩哔哩：撤销 v4.61 的开屏接口请求级 reject-dict。
# 流量日志证实：reject 返回 {} 会被 B 站客户端判定为请求失败并回退本地缓存的开屏素材，
# 且请求级 reject 会抢先于 [Body Rewrite]/[Map Local]，使其无法返回成功响应。
# 开屏接口现统一由下方 [Map Local] 返回「合法成功空列表响应」处理。
```

（`x/resource/peak/download` 的 reject-200 保留，它针对的是开屏素材下载，不是列表接口。）

### 2. 新增 [Map Local] 合法成功空响应（置于全局兜底之前，优先命中）

```
^https?:\/\/app\.bilibili\.com\/x\/v2\/splash\/(?:list|show|event\/list2|brand\/list)(?:\?.*)?$ data-type=text data="{\"code\":0,\"message\":\"0\",\"ttl\":1,\"data\":{\"show\":[],\"event_list\":[],\"brand_list\":[]}}" status-code=200 header="Content-Type:application/json"
```

要点：

- 返回 `code:0` 的标准成功响应，客户端按"接口成功但广告列表为空"处理，**不会再回退本地缓存**，且成功响应会覆盖/清空已缓存素材；
- 覆盖日志中实际出现的全部 4 个开屏端点（`list`/`show`/`event/list2`/`brand/list`），比 v4.61 还多覆盖 `brand/list`；
- 用 `data-type=text` + 完整 JSON 字符串，而非 `{}`；
- 放在 v4.54 全局开屏兜底（返回 `{}`）之前，保证 B 站请求优先命中专用规则。

### 3. 保留的双保险

- [Body Rewrite] 的 jq 净化（`.data.show = []` 等）保留：即使 Map Local 因某种原因未命中，真实响应仍会被净化为空列表且保留 `code:0` 外壳——两条路径都是"成功空响应"，方向一致，不再互相冲突。
- [Rule] 段 `upos-sz-static.bilivideo.com ...-1-SPLASH` 视频级开屏拦截、`api.biliapi.com/net` 域名拦截等全部保留。

### 保持不变

- 其余全部规则零改动、零删减（闲鱼前缀兜底、QUIC 拦截、MITM hostname 顺序均沿用 v4.61）；
- 文件由 v4.61 直接复制后仅做上述 2 处修改，结构完整：`[URL Rewrite]` L10 / `[Map Local]` L505 / `[Body Rewrite]` L764 / `[Script]` L889 / `[Rule]` L1066 / `[MITM]` L2992，共 2993 行。

## 验证

- 用日志中 10 条真实开屏请求逐条跑新正则：**全部命中**（`splash/list`、`splash/show`、`splash/event/list2`、`splash/brand/list`），信息流 `x/v2/feed/index` 正确不命中；
- 返回体 JSON 解析校验通过：`{"code":0,"message":"0","ttl":1,"data":{"show":[],"event_list":[],"brand_list":[]}}`；
- **规则优先级实证**：[Rule] 段第 1077 行的通用开屏 URL-REGEX（REJECT-DICT）同样能匹配这 4 个开屏 URL，但日志中 `brand/list` 同时命中该 [Rule] 正则与 v4.54 全局 Map Local 兜底时，实际由 **Map Local** 生效——证明 Shadowrocket 先求值 [URL Rewrite]/[Map Local]、再走 [Rule] 路由。因此新增的 B 站专用 Map Local 规则必然优先返回成功响应，不会被 [Rule] 层 REJECT 抢先。
